# Decisions Log — Ridgeline Contractor Portal

A running record of design and build decisions. **Append a new dated entry each working session** — don't overwrite old ones. This is the project's memory: when a choice is made (or reversed), log *what* was decided and *why*.

**Format:** newest entries at the top. Each entry = date, what changed, and the reasoning.

---

## How to use this file (AI + owner)

- Add an entry whenever you make a real decision: a design direction, a scope call, a data assumption, a tradeoff, a reversal.
- Keep entries short — a sentence or two of *what* and *why* is enough.
- Note reversals explicitly (e.g. "Changed from X to Y because…") so the history stays honest.
- Reference the relevant phase (see `IMPLEMENTATION_PLAN.md`) where useful.

### 2026-09-05 — `memory_bank/` renamed to `context/`; `BRIEF.md` lives at the repo root

- **Reverses the "relocated to `memory_bank/` ... to match this project's existing convention" call from earlier the same day** (see the entry below on consolidating `.impeccable.md`) — the owner moved `BRIEF.md` out to the repo root and asked for `memory_bank/` to be renamed `context/`, which makes this project's structure match the Charlotte (912 Days) project exactly: `BRIEF.md` + `IMPLEMENTATION_PLAN.md` at root, `context/` holding `decisions.md` and `PROMPTS.md`. Worth noting for the record since this project's own git history shows it went the *other* direction once before (an early commit message literally reads "Reorganized to put brief, prompts, to do, etc. into a context folder" — i.e. `context/` → `memory_bank/` happened at some point pre-dating this decisions log, and this change puts it back).

Left this file's own earlier entries pointing at `memory_bank/...` untouched — they're accurate descriptions of what was true when they were written; rewriting past entries to match today's paths would misrepresent the log's own history. `.github/copilot-instructions.md` needed no change — it already referenced `BRIEF.md` with no path prefix.

### 2026-09-05 — Job Detail header now surfaces Owner, Contractor, Sales Rep, and Roof System

- **"Roof System" (TPO/EPDM) is a new explicit field on the job, not derived at render time**, even though the owner described it as "based on the actual product they're using." Checked every job's actual quote line items first — each job's approved/draft quotes turned out to already be internally consistent (all-TPO or all-EPDM per job), so `jobs.json` got an explicit `roofSystem` field set to match what each job's real line items already say, rather than a live computation that would silently break for a Bid-stage job with no quote yet.
- **"Contractor" pulls from `profile.json`, not a new field** — this app is single-tenant (one contractor, Marcus Rivera / Rivera Roofing LLC) since the Phase 13 role/multi-contractor removal, so every job has the same contractor. Added a job-level field here would just duplicate `profile.json` and could drift out of sync with it.
- **"Owner" is genuinely new** — no prior field represented who owns the building being worked on (distinct from the contractor doing the work). Added `ownerName` per job with names that make sense for each property type (an HOA-style name for the condo complex, LLC-style names for commercial/industrial).
- **Reused the existing `jobs.detail.assigned_rep` i18n key** for the rep row instead of adding a duplicate "Sales Rep" key, since the Overview tab already establishes that label for the same data.
- **Updated `CreateJobView.vue` to collect Owner and Roof System too**, not just display them — otherwise a freshly created job would show blank/undefined in the very header block just added, the same failure mode as the Square Footage bug fixed in Phase 13. Owner is optional (falls back to "—"); Roof System defaults to TPO with an EPDM option, mirroring the only two systems that exist in the product catalog today.

### 2026-09-05 — "Add Photo" on inspection findings now actually works

- **Phase 9 shipped "Add Photo" as a styled but non-functional affordance** ("no file input required for demo," per the original `TODO.md` entry) — per direct request, wired it to a real `<input type="file" accept="image/*" multiple>` per finding in `InspectionFindingResponse.vue`, hidden and triggered by the existing button.
- **Deliberately omitted the `capture` attribute.** Adding `capture="environment"` would skip straight to the camera on most mobile browsers; leaving it off is what makes iOS/Android show their native action sheet (Take Photo / Photo Library / Choose File) — exactly the "ask which one" behavior requested — while desktop browsers show their normal file browser for the same markup. No platform-detection code needed; it's default `<input type="file">` behavior.
- **No backend exists to upload to**, so selected images are read client-side via `FileReader.readAsDataURL` and rendered as removable thumbnails staged under the button (each with an × to remove before submitting) — enough to make the interaction feel real and let a contractor correct a mis-selected photo, without inventing fake upload/progress UI for a request that never leaves the browser.

### 2026-09-05 — Page titled "Products," not "Catalog," in the UI

- **Renamed the visible title only, not the route or component.** `catalog.title` (and the unused `nav.catalog` key) changed from "Catalog"/translations to "Products"/translations across all 4 locales, per direct request. Left the route (`/catalog`), route name (`catalog`), and component (`CatalogView.vue`) as-is — renaming those too would touch `SearchView.vue`'s `ROUTE_MAP`/`QUICK_JUMPS`, `LibraryView.vue`'s "See All" target, and the file itself for a change that's purely about what a user reads on screen, not what the code is internally called. `BRIEF.md` §6 now calls this out explicitly so a future reader isn't confused by "Products page, route `/catalog`."

### 2026-09-05 — Consolidated `.impeccable.md` into `BRIEF.md`, then deleted it

- **`.impeccable.md` was ~90% duplicate of `BRIEF.md`'s own Design Direction section** (identical Brand Personality quote/3-words, identical color system, identical typography, identical references/anti-references, identical 5 design principles, identical outdoor-readability rules) — a second file drifting in and out of sync with the same content is a liability, not a safety net. Rather than keep both, merged the genuinely non-duplicate content into `BRIEF.md` and deleted the rest:

  - Added "WCAG AA minimum for all text contrast" as an explicit standard under Component Rules — the practical rules already achieved it, but the standard itself wasn't named anywhere in `BRIEF.md`.
  - Added "`@` resolves to `./src`" to the Tech Stack section — a real, verified-current technical fact with nowhere else to live.
  - Everything else (color tokens, typography, principles, references) was left alone in `BRIEF.md`, since `.impeccable.md`'s version was the duplicate, not the source of truth.

### 2026-09-05 — Catalog and Documents browse pages restored, with a two-tier twist (Phase 14)

- **Reversed a v5/v6 architectural decision, on purpose.** Phase 2/3 of the original build deliberately redirected `/catalog` and `/documents` to `/search`, reasoning that a unified global-search experience kept navigation to "one or two taps" and avoided a second, competing browse surface (see the now-deleted `ProductCatalogView.vue`/`DocumentLibraryView.vue`, and the design principle "the document library must be reachable in one or two taps from anywhere"). The owner explicitly asked for dedicated browse pages back, with richer filtering than before — so this reverses that call rather than quietly contradicting it. Both `LibraryView.vue`'s "See All" links and `SearchView.vue`'s "Jump to" tiles already pointed at `{ name: 'catalog' }`/`{ name: 'documents' }` the whole time (as did `QuickAccess.vue`'s "Docs" tile) — they'd just been dead-ending at an empty search screen since the redirect went in. Restoring real routes with those names made all three entry points work immediately with zero changes to those three files.
- **Rebuilt from the deleted views' own git history**, not from scratch — `git show HEAD:src/views/ProductCatalogView.vue`/`DocumentLibraryView.vue` (the deletion was staged but not yet committed at the time) had a solid single-tier filter+search+list pattern, closely matching `VideosView.vue`'s still-live pattern. Kept the search input styling, filter chip styling, and empty-state-with-clear-filters convention byte-for-byte; only the Catalog page's filtering got new structure.
- **Product category filtering went two-tier, Documents stayed one-tier.** The owner's request was specific: clicking a top-level group like "Membranes" should narrow the list *and* reveal a second row of more specific sub-filters (TPO / EPDM), while Documents just needed the existing PDS/SDS/Spec single-tier chips like Videos already has. Implemented as a UI-only `CATEGORY_GROUPS` map in `CatalogView.vue` (`Membranes: ['TPO Membrane', 'EPDM Membrane']`, the other 6 existing categories map 1:1 to themselves) — `products.json`'s `category` field is untouched, so `ProductCard`, `ProductDetailView`, and `useSearch` needed zero changes. The second filter row only renders when the active group maps to more than one category, which today is only ever Membranes; the other 6 groups behave like a normal single-tier filter.
- **Document previews went unique-per-document (19 total), not a shared 3-variant template.** Same bespoke-illustration bar as last session's 10 product SVGs, deliberately — a "sad," obviously-fake flat color block reading "PDS"/"SDS"/"Spec" was exactly what the owner flagged as wanting fixed, and a shared per-type template would still read as three interchangeable placeholders once you'd seen the first one of each. Each is a stylized fake-PDF "page" (drop shadow, colored masthead matching `DocTypeBadge`'s existing type-color mapping, the document's real name as a headline, a category-relevant motif reused/adapted from the corresponding product's illustration, a spec-sheet-style footer) at `public/documents/{id}.svg`, referenced via a new `previewUrl` field on each `documents.json` entry — same pattern as `products.json`'s `imageUrl` from last session.
- **Fixed two real, independently-discovered bugs while touching this code**, not asked for but directly adjacent to what was being changed:
  1. `DocumentCard.vue` recorded `routeName: 'documents', routeParams: {}` into Recently Viewed, so tapping a recently-viewed *document* sent you to the general Documents list instead of reopening the file — inconsistent with how `VideoCard.vue` already handles recently-viewed videos (opens the URL directly). Changed the stored entry to carry `fileUrl` and taught `RecentlyViewed.vue` to treat `type === 'document'` the same way it already treats `'video'`.
  2. `SearchView.vue`'s `ROUTE_MAP.documents` opened `item.url`, a field that doesn't exist on a `documents.json` entry (the real field is `fileUrl`) — so clicking a document search result silently opened `about:blank`. Fixed the field name and, while there, made it log to Recently Viewed too, matching the video branch right above it that already did.
- **Found and cleaned up leftover brand-fragment strings in `documents.json`'s `fileUrl` field** (e.g. `WB-TPO-60-PDS.pdf`, `SECTAPE-PDS.pdf`) — the Phase 13 rebrand pass replaced the visible `name`/`sku` fields but missed these placehold.co query-text params, since they're not rendered as UI text (the "file" just opens a blank placeholder page) and didn't show up in a text-content grep. Replaced with a generic `{doc.id}.pdf` pattern.
- **Found and cleaned up two leftover `carlisle_*` localStorage keys** (`useRecentlyViewed.js`, and a dead `InspectionResponseForm.vue` that Phase 9 replaced with `InspectionFindingResponse.vue` but never deleted) that the Phase 13 rebrand pass missed because a plain `grep -ri carlisle` across `.vue`/`.js` wasn't rerun after that pass — it was checked against `.md`/`.json`/`.html` at the time. Renamed the keys to `ridgeline_*` and deleted the dead component.
- **Restructured the AI-scaffolding docs to match the pattern from the Charlotte (912 Days) project**, per the owner's explicit request: a root-level `IMPLEMENTATION_PLAN.md` (phased `- [ ]`/`- [x]` checklist) and this file, `memory_bank/decisions.md` (dated, newest-first, append-only). `TODO.md`'s full phase history (1–13) was migrated into `IMPLEMENTATION_PLAN.md` verbatim in spirit, then `TODO.md` was deleted. `BRIEF.md` stays as the living spec/design doc, unlike Charlotte where it also plays that role — the split of responsibilities is the same, just relocated to `memory_bank/` instead of repo root to match this project's existing convention of centralizing AI scaffolding there.
- **`BRIEF.md` §6/§7/§11 updated to describe the real pages** instead of the "not a dedicated nav destination" / "redirects to Search" language from the reversed decision above, so the brief doesn't contradict what's actually built. Also fixed a stale §10 line still describing a "Role switcher (mirrored here from nav for convenience)" on the Profile page — a leftover the Phase 13 rebrand pass missed since it edited §6/§7/§11/Library Hub but not §10.

## Earlier history (Phases 1–13), condensed from `TODO.md` before it was retired

### Phase 13 — Rubric pass: rebrand, role removal, desktop nav, password gate, bugfixes

- **Removed the Contractor/Sales Rep role switcher entirely**, driven by a P303 rubric review — the case-study guide scopes P303 to a single mobile user journey, and the rep-facing views (approve/reject quotes, mark-inspection-reviewed, multi-contractor Home/Jobs views) were adding surface area without serving that journey. Rep identity survives only as read-only job data ("Assigned Rep").
- **Rebranded off Carlisle to a fictional manufacturer, Ridgeline** — the original brief used a real company (Carlisle SynTec) and several of its actual trademarked product lines (WeatherBond, Sure-Seal, FleeceBACK, CavGard, SecurTAPE, Sure-Grip, FlashBand), which isn't appropriate for a portfolio piece not affiliated with that company. Generic material descriptors replaced the brand-specific names; SKUs and `localStorage` keys were de-branded too.
- **Fixed a real, high-impact bug**: several views read the static `jobs.json` import directly instead of the reactive `useJobsData()` singleton `CreateJobView` writes to, so a newly created job was invisible everywhere except Search. Independently, a second bug meant a new job with blank Square Footage would crash its own detail page (`null.toLocaleString()`).
- **Built the desktop left sidebar nav** that `BRIEF.md` had specified from early on but that never actually got implemented — `SidebarNav.vue`, shown at the `md:` breakpoint in place of `BottomNav`.
- **Added a password gate** for the deployed demo, matching the pattern already validated on the Charlotte project.
- **Generated SVG product illustrations** for all 10 products, replacing flat `placehold.co` color blocks — no image-generation tool was available in the build environment, so bespoke vector illustrations (roll, board-stack, tape-roll, fastener cross-section, drip-edge coil, kit box, adhesive pail) were the closest fit to "real-looking" product art achievable without one.

### Phases 1–12 — Original v5/v6 feature build

- **Phase 1 (Reactive Data Layer):** introduced `useJobsData`/`useQuotesData`/`useOrdersData` as module-level singleton refs (no Pinia) specifically so records created at runtime (a new job, a new quote, a finalized order) would be visible everywhere reactively — the exact invariant Phase 13 later found had been violated by several views that bypassed the composables.
- **Phase 2/3 (Navigation Restructure + SearchView):** consolidated Catalog and Documents into Global Search only, reasoning that a unified search kept navigation to "one or two taps." (Reversed in Phase 14 above, at the owner's explicit request, once real two-tier/type filtering was wanted back.)
- **Phase 9 (Per-Finding Inspection Responses):** replaced a single whole-inspection response form with a per-finding response loop (`InspectionFindingResponse.vue`), since a real inspection can have multiple independent findings each needing its own remediation note and photo — a single shared textarea couldn't represent that.
- **Phase 10/11 (Library Hub + polish):** added a curated "Library" hub (Featured Products/Documents/Videos) as the bottom-nav destination for browsing, with a `featured: true` flag per data file for manual curation rather than an algorithmic "trending" concept, since the dataset is small and fictional.
- **Phase 12 (Floating Search Bar + Voice Search):** moved from a dedicated bottom-nav Search tab to a persistent floating search pill above `BottomNav`, freeing a tab slot for Library and making search reachable from every screen without competing for primary nav real estate. Voice search added as a progressive enhancement (Web Speech API), silently hidden on unsupported browsers rather than shown disabled.
